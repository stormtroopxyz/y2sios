# 05 — Metal on the Mali‑G77

**Priority: highest.** iOS 16 draws the wallpaper (PosterBoard), widgets, and many apps with **Metal**.
CoreAnimation itself is on the GPU through OpenGL ES (04‑gpu.md). Everything that insists on
Metal currently gets *no device* and draws nothing.

## What upstream already has (Adreno), and what of it carries over

Upstream built a Metal driver in three parts. Only the GPU-specific edges are freedreno's:

| Part | Upstream (Adreno) | For the Mali |
|---|---|---|
| **Shader compiler**: AIR (`.metallib` bitcode) → NIR, `tools/mesa/air/` (~20 k lines) | 456/456 modules read, 321 translated + validated, 30 run on the GPU, 552 `air.*` ops checked numerically | **Driver‑independent.** NIR goes to whichever Gallium driver: panfrost's Valhall compiler instead of ir3 |
| **GPU library** `libredwoodair.dylib`: `rwa_*` API, `air_metal.c` (7 k lines) | buffers, textures, samplers, compute + render pipelines, depth/stencil, argument buffers, IOSurface textures | **Generic Gallium.** The only freedreno parts are the screen open and its meson target. Ported: `GALLIUM_PANFROST` screen + `tools/mesa/air-panfrost.patch` |
| **Metal runtime** `RedwoodMetal.bundle`: `userland/src/redwoodmetal.m` (6.3 k lines) + `redwooddrawable.m` | `_MTLDevice` subclass registered through `MTLAddDevice`; encoders record, command buffers run; CAMetalLayer drawables | Uses `rwa_*` for everything. Its no‑GPU fallback speaks **msm** request numbers to `RedwoodGPU` and needs a panfrost path for `RedwoodMali` |
| Plug‑in discovery | `MetalPluginName` etc. on the `IOAcceleratorES` service, `metal=1` (`metal_props.c`, `MiniIOMobileFramebuffer.cpp`) | as is |
| `inject.c` | hides the Metal device from **backboardd** so CoreAnimation keeps OpenGL ES | keep: CA on GLES works; Metal is for the clients |

## Risks

- **Panfrost's compiler on AIR's NIR.** ir3 needed a few fixes (`air-ir3.patch`). Valhall's
  `bi_compile` will have its own. M1 measures it.
- **Tilebuffer and render targets.** Metal render passes map onto Gallium framebuffers. Panfrost's
  tiler heap is fully backed by the kernel (no growable heap), so a big render target may need a
  bigger heap BO.
- **Memory:** every Metal buffer is a write‑combined BO. Apps that read back a lot will be slow
  until cached + coherent BOs exist (G8).
- **M4 cost:** a system image rebuild and a 2.5 GB write per iteration. Batch it.

## Run 16 (25 October): the big batch -- CPU cost of a draw, the display without the CPU, throttling

Measured before (wifi run 11): GPU idle ~90 %, `commit` 8-27 ms of CPU per command buffer, `fb:` 4-16 ms of CPU
per frame (compare ~2.3 ms + scaling up to 10 ms), and at 81 C on the LITTLE zone every clock (GPU too) dropped to
its safe value (G3D 377 MHz) for the rest of the session.

- **UBO read extents** (air_metal.c `ubo_read_extents`): each compiled stage's furthest `load_ubo` per buffer
  (constant block and offset; otherwise unbounded), rounded to 16 + one vec4. `bind_stage` pads/uploads only that
  much instead of Gallium's 64 KB: a short binding was memcpy'd into 64 KB and then uploaded whole by
  `panfrost_emit_const_buf` (two 64 KB copies per buffer per draw); slot 0 / unaligned user buffers uploaded up to
  64 KB each draw. Zero past what was bound as before -- the run-15 glitches came from padding to the BINDING's
  size, which the shader reads past; the shader's own extent is what it can read. `RWA_UBO_EXTENT=0`: old behaviour.
- **panfrost-keepmap.patch**: a cached BO keeps its CPU mapping (unmapped in `panfrost_bo_free`), no
  evictable/unevictable MADVISE round trips (the kernel retains everything anyway): the ~12 % IOKit map/unmap
  churn. Per-BO, so no handle-reuse staleness (the run-15 shim cache keyed by handle could hand out a dead mapping).
- **fb_scaler=1 on** with the loader's display pool now 192/128/64 MB (up to 13 slots, cap 16).
- **Throttling per domain, Samsung's trips**: A55 by LITTLE 86/96, A76 by MID 86/96, GPU by G3D 88/100; step 1 a
  mid clock (1352/1612/572 MHz), step 2 safe; 6 degrees hysteresis.

### Run 16 results and run 17

Run 16: zero-copy on (`fb_scaler`: frames read by the controller, `fb:` 0.02-1 ms per frame instead of 4-16 ms,
no comparing, no scaling); home-screen swipes 37 command buffers/s with commit 5.5 ms (was 8+); the profile's
memmove from constant buffers gone (0.8 %), backboardd at 0.18 threads running on average. User: swiping faster,
wallpaper glitches while swiping, small hangs entering Settings and Control Centre.
- Glitch: the scaler's swap completed before the shadow update latched, so CoreAnimation drew into the surface the
  controller was still reading. `scalerShow()` now waits for the latch (≤ 1 frame) before the swap completes.
- Commit was synchronous: `mesa.finish` (flush + fence wait, 3-9 ms) inside every -commit. Now `rwa_submit` (flush,
  fence) at commit; `rwa_fence_wait` on one serial queue (com.redwood.metal.fences) marks COMPLETED and delivers the
  completed handlers in order; `-waitUntilCompleted` waits on the buffer's dispatch group; a completed handler added
  later is delivered on the group's notify. Display safety is the kernel's (`MiniIOSurfaceDrawn` before a swap
  shows a surface). `RWM_SYNC=1` restores the synchronous path.

### Run 19 -> 20: viewports, and the M5 cores

Run 19: swipes close to 60 fps (vsync in phase), but black bands on blurred materials, a black Maps, and the
Control Centre sliders' lower half glitching. The log had hundreds of "a viewport rectangle is not implemented
(asked for 352x128 / 176x64 / 88x32 / 44x16 at 0,0 of a 704x256 attachment)": CoreAnimation's blur builds its
pyramid in corners of one texture, and every level was drawn over the whole of it. `rwa_draw.viewport` (appended;
both static asserts at 304 bytes) carries -setViewport:'s rectangle per draw; the library's viewport maps clip
space onto it (y still negated, Metal's origin top left). Maps opens no RedwoodMali client at all (no Metal device
in the app): separate.
Cluster 2 (two Mongoose M5, 266 MHz as S-Boot leaves them) on: `cpumask=0xff dvfs_cl2=2304000`, asked last and
alone once every core is up and the TMU answers; checked again after; throttled by the BIG zone (1794 / 1196 MHz).

### Run 20 -> 21: the black band's real cause, and a governor

Run 20: Control Centre sliders fixed (viewports); M5s at 2304 MHz, ACPM kept answering; but the black band stayed,
and the phone ran hot (big zone 105 C at boot, 66-75 C with the GPU idle) with every cluster pinned at its top.
- The band: "no drawable: surface N has 1136 bytes a row, which is not a multiple of 64". CoreAnimation sizes the
  IOSurfaces it renders into by `-[MTLDevice iosurfaceTextureAlignmentBytes]`, which this driver never answered:
  16-byte rows (a quarter-width backdrop, 284 px = 1136 bytes) that Panfrost cannot import (v7+: 64), so the
  material's surface got no drawable and stayed black. Now 64 (and iosurfaceReadOnly..., minimumLinearTexture...,
  minimumTextureBuffer... 64).
- `dvfs_gov` (default on with dvfs=2): every 200 ms each cluster's busiest core (processor_info CPU_LOAD_INFO);
  ≥ 70 % busy: top rung at once; else the rung that makes it ~60 % busy, down one rung after 0.6 s; capped by the
  thermal step (now read every second). `governor:` line every 10 s with the average clocks.
- RC_JOBS=rc.jobs.manual: no scripted tour.
